## 1. 목표와 접근 방식

### 1.1 목표
1. **R1a 프로토타입**에서 일정·학원비 기록·입력 방식(웹 폼·엑셀 동기화 파일·채팅)의 실사용 가치를 검증한다. 주 사용자는 **엄마(iPhone)**.
2. 데이터는 처음부터 **두 저장 모드(GitHub / Firebase)** 를 지원하고, 실사용으로 주 모드를 정한다 (D-13).
3. 검증 후 R1b에서 푸시 알림·서버 기능(Blaze)을 붙인다.

### 1.2 개발 원칙
| 원칙 | 내용 |
|---|---|
| 저장소 교체 가능 | 화면·도메인 로직은 `Repository` 인터페이스만 사용. 구현 3종: `GitHubRepository`, `FirestoreRepository`, `MemoryRepository`(테스트) |
| 같은 계약, 같은 테스트 | 저장소 **공통 계약 테스트**를 세 구현에 모두 실행 → 두 모드의 동작이 같음을 보장 |

## 3. 핵심 설계

### 3.1 Repository 인터페이스
```ts
interface Repository {
  mode: 'github' | 'firebase' | 'memory';
  watch<T>(col: Collection, q?: Query): Observable<T[]>;     // GitHub: 폴링 기반, Firebase: 실시간
  get<T>(col: Collection, id: string): Promise<T | undefined>;
  create<T>(col: Collection, id: string, data: T): Promise<'created' | 'exists'>;  // id 고정 → 멱등
  update<T>(col: Collection, id: string, patch: Partial<T>, expectVersion: number): Promise<'ok' | 'conflict'>;
  applyBatch(ops: Op[], meta: { label: string; by: MemberId }): Promise<BatchResult>; // 원자적
  revertBatch(batchId: string): Promise<RevertResult>;          // 충돌 항목은 보고
  pending(): Observable<{ count: number; failed: number }>;     // X-14, U-12
  flush(timeoutMs: number): Promise<boolean>;                    // 로그아웃·모드 전환 전
}
```
- **id 고정 create** = 청구(`billKey`), 납부·수령 기록(확인 시 생성한 ULID) 모두 재전송해도 1건 (Codex v1.1 #4·#7).
- **update는 version 검사** — 다르면 `conflict` → 화면에서 최신값 보여주고 선택.
- 금전 기록의 "삭제" = `update`로 `voided` 필드만 추가 (규칙에서 다른 필드 변경 금지).

### 3.2 GitHub 모드 (`src/data/github`)
| 동작 | 방법 |
|---|---|
| 처음 불러오기 | `GET /repos/{o}/ai-note-data/git/trees/main?recursive=1` → 파일별 blob sha 목록 → blob 받아 캐시(Dexie) |
| 변경 확인 | 앱 열 때·화면 복귀·열려 있는 동안 60초마다 트리 조회 (ETag 조건부 요청 → 변경 없으면 304) → sha가 바뀐 파일만 다시 받음 |
| 1건 저장 | `PUT /contents/data/...json` (기존 파일이면 sha 포함) → 커밋 메시지 `[엄마 아이폰] 납부 기록: 딸 영어 11월분` |
| 동시 수정 충돌 | sha 불일치(409) → 최신 파일 받아 version 비교 → 금전 기록은 경로가 달라 충돌 없음, 일반 항목은 충돌 안내 |
| 여러 건 원자 저장 (엑셀 가져오기, 모드 이동) | Git Data API: blob 생성 → tree(base_tree) → commit → `PATCH refs/heads/main` (fast-forward 실패 시 최신 기준으로 다시 시도) → **커밋 1개** |
| 가져오기 되돌리기 | 해당 커밋의 변경 경로를 이전 blob으로 되돌리는 새 커밋. 현재 sha ≠ 가져오기 직후 sha 인 파일은 충돌 목록 |
| 오프라인 | 저장은 Dexie 전송대기열(operationId)에 넣고 연결 시 순서대로 전송, 화면엔 "전송 대기 n건" |
| 자녀 사본 (Q15, G-03) | 일정·장소·학원(비용 제외) 저장 시 대상 자녀의 `ai-note-son/daughter` 저장소에 **본인 관련 항목만** 함께 커밋. 비용·형제 데이터 경로는 사본 생성기에서 원천 제외 + 테스트 |
| 토큰 | 기기 IndexedDB 저장, 화면 재표시 없음, 백업·내보내기 제외. 응답 헤더의 토큰 만료일을 읽어 14일 전 경고 |
| 한도 | 토큰당 시간당 5,000회 — 304 응답 활용, 평상시 시간당 수십~수백 회 예상 |

### 3.3 Firebase 모드 (`src/data/firebase`)
컬렉션: `families/{fid}/` 아래 `members, accounts, joinRequests, places, academies, enrollments, events, holidays, notifications` + 부모 전용 `private/finance/{enrollmentCosts, paymentInfos, bills, payments, adjustments, refunds, receipts, expenses, categories, auditLogs, importBatches}`.

**보안 규칙 설계 (Codex v1.0 #1~3, v1.1 #5·#16)**
| 대상 | 규칙 |
|---|---|
| 계정 연결 | `accounts/{uid}` → `{ memberId, role }`. 규칙 함수 `me()` = 이 문서. 역할·memberId는 부모만 쓰기 |
| 가족 생성 | `families/{fid}` + `members/{memberId}` + `accounts/{uid}`(role=parent)를 **한 배치**로 생성. 규칙에서 `getAfter()`로 세 문서가 서로 일치하는지 검사, 이미 있는 가족에는 불가 |
| 가입 | 누구나 `joinRequests/{uid}`만 생성(역할 필드 금지). 부모가 승인하면 `members`·`accounts` 생성 |
| 일정 읽기 | 부모: `scope != 'self'` 또는 작성자 본인. 자녀: `visibleTo`에 내 memberId 포함 |
| 일정 쓰기 | 자녀: 본인만 대상인 일정 생성. 수정 시 `createdBy·targets·visibleTo·scope·enrollmentId` 불변(`diff().affectedKeys()`) |
| 비용 영역 | 부모만. **컬렉션별 동작을 따로 정의**(넓은 `private/**` 쓰기 허용 금지): payments·receipts·adjustments = create(기록자=나, 시각=서버) + update는 `voided` 필드 추가만 / auditLogs·importBatches = create만 / bills 등 일반 = 부모 create·update |
| 알림 설정 | 자녀는 자기 `members/{memberId}.notifyEnabled`만 수정 |

### 3.4 모드 이동 (`src/io/migrate`, D-M2·D-M3)
- 원본 전체 읽기 → 대상이 비었는지 확인(아니면 대상 JSON 백업 후 확인) → 같은 경로·ID로 일괄 쓰기 → **건수·금액 합계·참조 무결성 대조표** 표시.
- GitHub → Firebase 시 구성원은 memberId 유지, 각자 Firebase 계정 생성 후 `accounts`로 연결(U-13). 과거 기록자(memberId)는 그대로 보존, `migratedBy/At` 추가.
- 중단 후 재실행해도 같은 ID 덮어쓰기라 중복 없음.

```
Bill (id = billKey = `${enrollmentId}:${periodStart}`)
  payments[]     (별도 문서, bill 참조)  { id, paidOn, amount, method, card?, by, at, voided? , replacedBy? }
  adjustments[]  (별도 문서)            { id, amount, reason, by, at, voided? }
  refunds[]      (별도 문서)            { id, causeDate, requestedOn, reason, requested, agreed?,
                                          manualClose?{reason,by,at}, withdrawn? }
    receipts[]   (별도 문서)            { id, receivedOn, amount, method, by, at, voided? }
```
- **계산값 (저장 안 함)**: 납부합 = Σ유효 payments, 조정합 = Σ유효 adjustments, 남은 금액 = 금액 − 조정합 − 납부합, 환불 잔액 = (agreed ?? requested) − Σ유효 receipts, 종결 = 잔액 ≤ 0 또는 manualClose 또는 withdrawn.
- **표시 상태** (Requirement 4.2): 취소 → 환불진행/환불완료 → 납부완료(조정 포함) → 부분납부 → 미납(기한 경과) → 예정. 남은 금액은 **기한 전 잔액 / 연체 잔액**으로 구분 표시 (Codex v1.1 #20).
- **청구 생성**: 비용 화면 진입 시 "지난 2개월 ~ 다음 달" 범위 `create(billKey)` — 있으면 건드리지 않음. 기간 **전체** 휴원이면 생성 안 함, **일부** 휴원이면 생성 + `needsReview` (A-13). 적용 시작일 기준 요금 선택 (A-08).
- **법정 기한 참고** = causeDate + 5일 (F-17, "참고" 표기).

### 3.6 반복 일정 (`domain/recurrence`)
- 원본: RRULE(서울 로컬 시각) + 예외 맵. 회차 키 = `${eventId}@${원래 시작 ISO}` (S-13).
- 조회: 활성 반복 원본 전체 + 기간 내 1회성 → 클라이언트 전개. 이동 예외는 새 시각 기준 필터.
- 수정 범위: 이번만 / 이후 모두(분할 + 예외·보강·준비물 체크 이관) / 전체.
- 휴일: 자녀(학교)별 (S-14). 휴강·결석은 비용 자동 반영 없음 (S-04).
- 준비물 (S-16): 원본에 기본 목록, 회차별 체크 상태 `checks[occurrenceKey]`.
- 실시간 상태 (`domain/liveStatus`, S-V1): `(occurrences, now, memberId) → IN_CLASS(종료까지 n분) | GAP(다음까지 n분, 자투리) | DONE`.

### 3.7 입력 공통 구조
```
 웹 폼 ──────┐
 엑셀 행 ────┼─▶ normalize() ─▶ zod 검증 ─▶ resolver(참조 연결) ─▶ 확인 카드 ─▶ Repository
 채팅 답 ────┤        │경고(원래 값 표시)      │실패: 오류/되묻기     │후보 여러 개: 선택지
 붙여넣기 ───┘
```
- `normalize()`: "월수금" → [월,수,금], "32만"·"320,000원" → 320000, "7시~9시" → 학원 일정이면 19:00–21:00으로 추정 **+ 확인 카드에 원문 표시**, "다음주 화요일"·"오늘" → 날짜.
- **붙여넣기 파서** (`io/paste`, I-04): 금액 `(\d{1,3}(,\d{3})+|\d+)\s*원|\d+\s*만\s*원?`, URL `https?://\S+`, 대상 월 `(\d{1,2})월(분)?`, 기한 `(\d{1,2})[./월]\s*(\d{1,2})일?\s*까지`, 학원명 = 등록된 학원명·별칭과 유사도 매칭. 추출 결과 → 해당 청구에 금액·이달 납부 링크 채움 또는 새 청구 제안 → 빠진 항목은 안내형 질문으로.
- **안내형 채팅** (`chat/guided`): 입력 종류 칩 → 스키마의 필수 필드 순서대로 질문 → 첫 문장에 알려진 단어가 있으면 미리 채움 → 해석 못한 텍스트는 메모로 보존 → 확인 카드 → 저장.

### 3.8 엑셀 동기화 파일 (`io/excel`, I-11~I-20, I-30)
- **내보내기 구성**: [정보] 시트(내보낸 시각, 모드, 가족, schemaVersion, **엑셀에 포함되지 않는 항목 목록**) + 데이터 시트(I-30 목록). 각 행 숨김 열 `ID`, `version`, `수정시각`; 참조는 이름 열 + 숨김 참조 ID 열.
- **가져오기 비교 규칙**
  | 파일 행 | 현재 데이터 | 결과 |
  |---|---|---|
  | ID 없음 | — | 신규 (자연키 일치 시 "중복 후보") |
  | ID 있음, 값 같음 | — | 변경 없음 |
  | ID 있음, 값 다름, 파일 version = 현재 version | | **수정** |
  | ID 있음, 값 다름, 파일 version < 현재 version | 앱에서도 수정됨 | **충돌** → [파일 값] / [앱 값] |
  | 파일에 없음 | 현재 있음 | 삭제하지 않음, "파일에 없음" 목록 |
  | 금전 기록 행 수정 | | 원 기록 취소 + 새 기록 (F-34) |
- 반영은 `applyBatch` 1회 (GitHub: 커밋 1개). 배치 기록에 항목별 이전 값·파생 항목(자동 생성 청구 등) 저장 → `revertBatch`.
- 폰에서는 내보내기·미리보기 지원, 편집은 PC 권장 안내 (I-10).

### 3.9 PWA 설치·오프라인 (D-10, X-12, Q-14, Q-16)
