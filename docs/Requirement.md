## 0. 개요

### 0.1 배경
- 자녀 2명(아들 고1, 딸 중1)이 여러 학원을 다녀 일정·학원비·숙제·시험 관리가 복잡하다.
- 학원비 납부 여부, 환불 처리 여부가 기억·메모·문자에 흩어져 누락 위험이 있다.
- 가족 기기: iPhone 1대(엄마), Android 3대(아빠·아들·딸).

### 0.2 1차 핵심 목표 ★
> **일정과 비용(특히 학원비 납부·환불 기록)을 폰에서 한눈에 인지하고, 쉽게 입력·수정해서 실제로 계속 쓰게 만든다.**

### 1.5 저장 모드 (D-13) 🆕

#### 1.5.1 두 모드 비교
| 항목 | ① GitHub 모드 | ② Firebase 모드 |
|---|---|---|
| 데이터 위치 | 비공개 저장소 `etin94-prog/ai-note-data` 의 JSON 파일 | Firestore (Spark 무료) |
| 로그인 | 기기별 **GitHub 토큰** 1회 입력 (아빠가 저장소 전용 토큰 발급) | 이메일 + 비밀번호 |
| 동기화 | **앱 열 때 + 화면 복귀 시 + 열려 있는 동안 1분마다** 가져오기, 저장 즉시 올리기 | **실시간** (수 초) |
| 변경 이력 | **Git 커밋 = 변경 이력** (GitHub 웹에서 누가 언제 무엇을 바꿨는지 확인, 되돌리기) | 앱 내 변경 이력(AuditLog) |
| 오프라인 | 기기 캐시로 조회·입력, 연결 시 올리기 | 동일 |
| 권한 강제 | 저장소 단위 → **부모 기기 전용** (1.5.3) | 서버 보안 규칙으로 역할별 강제 |
| 자녀 사용 | 제한 (1.5.3) | ✅ |
| 비용 | 0원 | 0원 (Spark) |
| 설정 난이도 | 아빠에게 익숙 | 가이드 따라 1회 설정 ([가이드](guide/Firebase_설정가이드.md)) |

| ID | 요구사항 | 릴리스 |
|---|---|---|
| D-M1 | 화면·기능은 두 모드에서 **동일**. 모드는 가족 설정에서 선택 | R1a |

#### 1.5.3 GitHub 모드의 권한·제약
| ID | 요구사항 | 릴리스 |
|---|---|---|
| G-01 | 토큰은 **`ai-note-data` 저장소 하나에만, 내용 읽기/쓰기 권한**으로 발급 (fine-grained token), 만료일 설정. 기기마다 이름 붙여 발급 (예: "엄마 아이폰") → 분실 시 해당 토큰만 폐기 | R1a |
| G-02 | GitHub 토큰은 저장소 단위라 파일별 권한을 나눌 수 없음 → **GitHub 모드는 부모 기기(엄마·아빠·PC) 전용** | R1a |
| G-03 | 자녀 기기 (GitHub 모드일 때): 부모 앱이 저장할 때 **자녀별 비공개 저장소**(`ai-note-son`, `ai-note-daughter`)에 **본인 일정만 담은 읽기 전용 사본**을 함께 올림. 자녀 기기는 자기 저장소 **읽기 전용 토큰**만 가짐 → 비용·형제 일정 원천 차단 | R1a 🔸 (Q15) |
| G-04 | 자녀의 쓰기(준비물 체크, 알림 켜기/끄기)는 GitHub 모드에서는 **미지원** — Firebase 모드에서 지원 | R1a |

## 4. 비용 (Cost) — 부모 전용 ★

> **원칙 (D-03): 이 앱은 결제·환불을 직접 처리하지 않는다.** 실제 납부는 학원 링크·앱·계좌이체로 하고, 앱은 **무엇을 냈고, 안 냈고, 돌려받을 돈이 얼마인지 기록·추적**한다.

### 4.1 개념
| 개념 | 설명 |
|---|---|
| 청구 (Bill) | 학원에 낼 돈 1건. **대상 기간**(예: 11월분)과 **납부 기한**을 가짐. 자동 또는 수동 생성 |
| 납부 기록 (Payment) | 실제로 낸 기록 1건. 청구 1건에 여러 건 가능(부분 납부). **건별 고유 ID, 추가 방식** |
| 환불 건 (Refund) | 청구에 연결된 반환 추적. 요청액·합의액·수령 기록 여러 건·잔액·종결 여부 |
| 환불 수령 기록 (RefundReceipt) | 실제로 돌려받은 기록 1건 (분할 수령 가능) |
| 기타 지출 (Expense) | 교재비, 교통비, 간식 등 청구가 아닌 지출 |

> 원본은 아빠 PC의 로컬 폴더에만 보관 (개인정보 포함, 저장소에 복사 금지). 테스트는 형식만 흉내 낸 가상 샘플 사용.

**관찰**
1. **같은 청구 안내가 여러 번 반복 발송**됨 (예: 같은 금액을 며칠 간격으로 2~4회) → 재발송을 하나의 청구로 합쳐야 함
2. 금액이 매달 다름(특강·교재·방학) → 수강 정보로 자동 생성한 "예상 청구"보다 **학원이 보낸 실제 청구가 정확** → 카톡 청구를 우선 원천으로
3. 학생명이 학원마다 다르게 표기됨 (예: 이름 뒤 A/B/C, 학교명 괄호, "○○아빠…") → **자녀별 별칭 목록** 필요
4. 학원명도 표기가 다름 (채널명 / 《》 안 이름 / 법인명 "(주)…") → **학원별 별칭 목록** 필요
5. 형식 B는 **납부 완료 메시지가 없음** → 납부 확인은 카드 내역·결제선생 완료 메시지·수동 기록으로
6. 결제 취소(환불) 메시지가 있음 → 환불 수령 기록으로 연결
7. 카톡 내보내기 텍스트에는 **납부 버튼 링크가 없음** → [납부하러 가기]는 "카톡에서 해당 학원 채널 열기" 안내로 대체 (A-12 ② 보완)

### 6.4 R1a 알림의 제약과 보완
- 웹은 **서버 없이 정해진 시각에 푸시를 보낼 수 없음** → R1a에서는:
  1. 앱을 열면 **알림함·처리 필요 배너**에 다가오는 일정·기한을 표시 (N-13)
  2. 앱이 열려 있는 동안에는 브라우저 알림 표시 (권한 허용 시)
  3. **캘린더 내보내기(.ics, S-15)**: 6.2 설정의 알림 시점을 포함해 폰 캘린더에 넣으면 캘린더 앱이 알림. 단, 캘린더 앱에 따라 알림 시점이 무시될 수 있음 → Sprint 0에서 Android(구글 캘린더)·iPhone(캘린더) 실제 확인
- 정시 푸시는 R1b(Firebase)에서 제공.

 ├─ ReminderPolicy{ memberId, 일정종류, offsets[분] }            ← 부모만 수정
 ├─ Place         { 이름, 주소, (R3)좌표 }
 ├─ Holiday       { memberIds[] 또는 학교placeId, 시작, 종료, 이름 }       🆕 자녀(학교)별
 ├─ Academy       { 이름, 과목[], placeId, 전화, 강사, 메모, 상태 }
 │   └─ PaymentInfo { 납부유형(A-12), 고정URL, 은행, 계좌번호, 예금주, 결제앱, 담당부모(기본 아빠), 메모 }  ← 부모 전용
 ├─ Enrollment    { childId, academyId, 과정명, 시간표[{요일, 시작, 종료}],

 ├─ EnrollmentCost{ enrollmentId, 적용시작일, 금액, 주기, 결제일, 선납/후납,

 ├─ CardTxn       { 지문, 카드명, 승인일시, 금액, 가맹점, 취소여부, 짝지은 paymentId? }  🆕 C-01·C-02   ← 부모 전용

공통 필드: `id`(ULID, 청구는 `billKey`), `createdAt`, `updatedAt`, `updatedBy`(memberId), `version`(수정할 때마다 +1, 충돌 판정용), `schemaVersion`. 금액은 원 단위 정수.

**저장 경로 규칙 (두 모드 공통)**: `{컬렉션}/{id}` — Firestore는 `families/{fid}/{컬렉션}/{id}` 문서, GitHub는 `data/{컬렉션}/{id}.json` 파일. 비용 데이터는 `private/` 아래(Firestore 규칙으로 부모 전용, GitHub는 부모 전용 저장소).
