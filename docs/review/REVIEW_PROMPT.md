# 리뷰 요청: 가족 학원·학습 관리 앱 — 요구사항 & 구현계획 검토

당신은 **시니어 모바일/웹 앱 아키텍트이자 제품 기획 리뷰어**입니다.
아래 두 문서를 읽고, **구현을 시작하기 전에** 문제점과 개선점을 찾아주세요.

## 읽을 문서
파일에 접근할 수 있는 환경(Claude Code, Codex, Gemini CLI 등)이라면 저장소 루트 기준으로 다음 파일을 직접 읽으세요.
1. `docs/Requirement.md` — 요구사항 정의서
2. `docs/구현계획서.md` — 구현 계획서

파일 접근이 안 되는 채팅 환경이라면, 이 프롬프트 아래에 두 문서 전문이 이어서 붙어 있습니다 (`review-bundle.md`).

## 배경 (요약)
- 사용자: 부모 2명(아빠 Android, 엄마 iPhone), 자녀 2명(고1 아들, 중1 딸, 둘 다 Android). 1인 개발자(아빠) + AI 보조.
- **1차 핵심 목표**: 일정과 비용(특히 학원비 납부·환불 여부)을 폰에서 한눈에 인지하고 쉽게 입력·수정해서 실제로 계속 쓰게 만드는 것.
- 확정 사항: 비용은 부모만 열람, 형제간 일정·숙제·시험 비공개, 저장소 `ai-note`(공개, GitHub Pages).
- 기술 방향: Expo(React Native + Web), GitHub Pages 웹앱(PWA, 홈 화면 아이콘 실행). R4에서 Android APK/iOS 네이티브 앱.
- 최신 결정은 `docs/Requirement.md` 0.5장 결정 기록(D-01~)을 기준으로 하세요. 특히 **저장 모드 2가지(GitHub 비공개 저장소 / Firebase Spark)를 처음부터 지원**(D-13), 납부·환불은 기록만(D-03), 입력 3종(D-06·D-11), 안내형 채팅 먼저(D-08), 주 사용자 엄마 iPhone(D-07).
- 이전 리뷰 결과(`docs/review/리뷰결과_*.md`)와 그 반영 내역(Requirement 18장)도 참고해, **이미 반영된 지적을 반복하지 말고 새 문제에 집중**하세요.
- 설정 가이드: `docs/guide/Firebase_설정가이드.md`, `docs/guide/GitHub_데이터저장소_가이드.md`

## 검토 관점 (각 관점마다 반드시 확인)
1. **1차 목표 적합성**: R1 범위가 "일정 + 학원비 납부·환불 인지·입력"이라는 목표에 집중되어 있는가? 빠진 것 / 과한 것은?
2. **요구사항 완결성·명확성**: 모호하거나 테스트 불가능한 요구사항, 서로 충돌하는 요구사항, 누락된 예외 상황(예: 학원 결제 방식, 형제 할인, 중도 등록 일할 계산, 휴원 중 청구, 환불 후 재등록 등).
3. **요구사항 ↔ 구현계획 일치**: 요구사항 ID가 구현계획의 스프린트·설계에 모두 반영되었는가? 계획에만 있고 요구사항에 없는 것은?
4. **보안·개인정보**: Firestore 보안 규칙 설계(비용 분리, `visibleTo` 방식, 역할 변경 방지)에 허점이 있는가? 공개 저장소 운영 위험은?
5. **기술적 타당성**: Expo web export + GitHub Pages 하위 경로, iOS PWA 웹 푸시, Firebase Auth 도메인 문제, 반복 일정(RRULE + 예외) 설계, 청구 결정적 ID 방식, 5분 스케줄러 알림 방식, Blaze 미전환 시 GitHub Actions 대체안의 현실성.
6. **모바일 UX**: "납부 체크 2탭, 지출 입력 15초" 같은 기준이 현실적인가? 화면 구성·내비게이션 개선점. 자녀가 거부감 없이 쓸 수 있는가?
7. **일정·범위 현실성**: 1인 개발(주 10~15시간) 기준 스프린트 기간이 현실적인가? R1을 더 줄이거나 쪼개야 하는가?
8. **한국 환경 특이사항**: 학원비 결제 관행, 학원법 교습비 반환 기준 해석(Requirement 4.6), 국내 지도·교통 API 선택(카카오, ODsay, 네이버) 및 제약.
9. **운영·비용·리스크**: 놓친 리스크, 비용 폭증 가능성, 백업·복구, 유지보수 부담.
10. **대안 제시**: 더 단순하거나 더 나은 접근이 있다면 근거와 함께 제시 (단, 확정 사항은 존중).

## 출력 형식 (반드시 이 형식, 한국어)

### 1. 총평 (5줄 이내)
- 전체 평가, 구현 착수 가능 여부: `착수 가능` / `수정 후 착수` / `재설계 필요`

### 2. 지적 사항 표
| # | 심각도 | 관점(1~10) | 문서·위치 (예: Requirement F-03, 구현계획서 3.4) | 문제 | 근거 | 제안 |
|---|---|---|---|---|---|---|

- 심각도 기준
  - **Critical**: 구현 전 반드시 수정 (보안 구멍, 목표 달성 불가, 기술적으로 불가능)
  - **Major**: 수정 강력 권장 (큰 재작업·사용 중단 위험)
  - **Minor**: 개선하면 좋음
  - **Question**: 사용자 확인이 필요한 질문
- 심각도 높은 순으로 정렬.

### 3. 누락된 요구사항 제안
- 요구사항 ID 체계에 맞춰 제안 (예: `F-16 (신규) …`), 릴리스(R1~R4) 표기.

### 4. R1 범위 조정 의견
- R1에서 빼도 되는 것 / 반드시 넣어야 하는 것.

### 5. 미결 사항(Requirement 16장, 구현계획서 10장)에 대한 의견
- 각 항목에 권장 결정과 이유.
